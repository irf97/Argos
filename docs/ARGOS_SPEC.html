ARGOS Operational Specification

A local-first memory substrate for AI agents: one desktop daemon, one Postgres source of truth, many MCP and HTTP clients.

Spec Snapshot

Runtime Phoenix server on 127.0.0.1:4020
Storage Local Postgres database argos_dev
MCP POST /mcp plus Claude stdio bridge
Boundary Capture fast; slow work happens after capture

1. Intent

ARGOS is not a model's internal memory. ARGOS is an external, auditable memory backend that agents can call through MCP or HTTP. The model remains an execution client. ARGOS owns storage, validation, retrieval, and approval-gated durable state changes.

Goal

Shared local memory

Claude, GPT clients, Codex, local agents, and browser tools use the same desktop data source.

Rule

One process

Run one ARGOS Phoenix daemon. Do not spawn a separate memory server per agent.

Boundary

No hidden autonomy

Canon changes, risky proposals, and durable doctrine mutations require operator approval.

2. Runtime Topology

ARGOS is a desktop hub. Every client routes through the Phoenix server, and Phoenix is the only process that writes memory data to Postgres.

Claude Desktop
->
stdio bridge -> HTTP MCP -> Phoenix -> Postgres
OpenAI/GPT client
->
HTTP MCP -> Phoenix -> Postgres
Local backend
->
HTTP API -> Phoenix -> Postgres
Browser/operator
->

ARGOS_URL=http://127.0.0.1:4020
ARGOS_MCP_URL=http://127.0.0.1:4020/mcp

Use 127.0.0.1 instead of localhost so all clients resolve the same loopback target.

4. Memory Write Flow

Capture is the most important path. It must be fast, transactional, and local. It should not wait on external agents, embedders, crawlers, web requests, or long-running workers.

  1. Client calls argos_capture or POST /api/capture.
  2. ARGOS validates shape, kind, canon, source, payload, and author.
  3. ARGOS opens a short Postgres transaction.
  4. ARGOS locks the relevant canon chain.
  5. ARGOS computes prev_hash and deterministic hash.
  6. ARGOS inserts an append-only event.
  7. ARGOS returns the event result quickly.
  8. Optional slow follow-up work is queued after the event exists.
The write path must never hold a DB connection while waiting on downstream AI work. That failure can starve the pool and make reads hang behind a stuck capture.

5. Invariants

Invariant Reason Violation Signal
One Phoenix app Keep supervision, routing, and data ownership simple. Multiple competing memory servers or conflicting ports.
One Postgres database Postgres is the source of truth. Agents storing memory in separate files or direct side tables.
Events are append-only Memory must be auditable. Update/delete operations against historical events.
Event hashes are deterministic Mutation should be detectable. Same event material produces a different hash.
Events are hash-linked per canon Chain validation proves ordering and continuity. Wrong prev_hash or chain reconstruction failure.
Canon commits require approval Durable doctrine changes need operator control. Autonomous canon mutation without an approval record.
Agents do not write Postgres directly ARGOS must enforce validation and hash-chain logic. Client credentials or direct SQL writes outside Phoenix.
Loopback by default Desktop memory should remain private unless explicitly exposed. Binding to 0.0.0.0 without auth or private network controls.

6. Client Permission Model

Client Type Allowed Surface Default Trust
Remote GPT or web connector search, fetch Read-only unless explicitly approved.
Claude Desktop stdio bridge to local MCP tools May write low-stakes events if operator asks.
Codex/local coding agent HTTP MCP or HTTP API Can capture implementation events and request context packs.
Planning or review agent argos_propose, read tools Creates proposals, does not commit canon changes.
Browser/operator LiveView approvals and HTTP API Final authority for approvals and durable state changes.

7. Failure Modes

Failure Severity Symptom Likely Cause First Check
ARGOS process down High Connection refused, no tools visible. Daemon not started or crashed. scripts\status-argos.ps1
Wrong URL or port High Client configured but calls fail. Using localhost, old port, or wrong env var. ARGOS_MCP_URL, client config.
Claude bridge failure Medium Claude sees no ARGOS tools or tool calls time out. Python bridge error, bad config, ARGOS not reachable. .argos/argos-mcp-stdio.log
Postgres unavailable High Server starts poorly, writes fail, migrations fail. DB service stopped, wrong user, missing database. mix ecto.migrate
DB pool starvation High One write hangs; later reads hang too. Connection held while waiting on slow downstream work. Restart ARGOS, inspect write handler logs.
Capture timeout High argos_capture hangs for minutes. Capture path synchronously awaits worker, embedder, or crawler. Ensure capture returns after DB insert.
Search empty after capture Medium Event exists but search returns no results. Search query, index coverage, or MCP visible store mismatch. GET /api/events, then MCP search.
Hash-chain conflict High Wrong prev_hash or validation failure. Concurrent writes not serialized per canon. Chain validation tests and transaction locking.
Config overwrite Medium Existing MCP servers disappear. Client config rewritten instead of merged. Backup config, merge under mcpServers.
Remote connector cannot reach desktop Low ChatGPT web cannot connect to 127.0.0.1. Cloud client cannot see desktop loopback. Use HTTPS tunnel with auth if remote access is needed.

9. Acceptance Criteria

  • scripts\status-argos.ps1 reports health_ok: true.
  • MCP tools/list returns the ARGOS tools.
  • argos_capture writes an event quickly.
  • search and fetch can retrieve a captured event.
  • mix test passes.
  • Claude config contains existing MCP servers plus argos.
  • Startup launcher exists for the desktop user.
  • No client writes directly to Postgres.
